# Préparation VPS — port 8010

La cible demandée est `/var/www/caspay-all/admin`. Ce nom diffère de `/var/www/cashpay-all/...` dans les logs du service client : le chemin doit être contrôlé sur le VPS. Le back-office est configuré sur **127.0.0.1:8010**, publié en HTTPS par Nginx sur **admin.cashpay-all.com**. Ne pas ouvrir directement 8010 sur Internet.

Aucun mot de passe communiqué dans la conversation n’est repris dans ces fichiers. L’accès SSH distant n’a pas été effectué depuis l’environnement de travail, dont le réseau ne dispose pas de chemin TCP/SSH autorisé vers le VPS. Les étapes suivantes sont préparées pour le terminal du serveur ou une session sécurisée disposant de cet accès.

## Contrôles avant installation

- Vérifier le répertoire demandé et les éventuels clones existants ; réutiliser un clone propre après contrôle de son remote et de sa révision, ne pas écraser un projet existant.
- Vérifier `node --version` (22.9 minimum), `npm --version`, `pm2 --version` et `nginx -t`.
- Vérifier avec `ss -ltnp '( sport = :8010 )'` que le port n’appartient pas à une autre application. Ne tuer aucun service pour libérer ce port sans identification.
- Vérifier le DNS `admin.cashpay-all.com`, son certificat et l’absence d’une configuration Nginx concurrente pour ce domaine.

## Nouveau répertoire uniquement

Si le chemin n’existe pas, et avec un accès GitHub déjà autorisé sur le VPS :

```bash
bash -eu <<'ADMIN_INSTALL'
test ! -e /var/www/caspay-all/admin
mkdir -p /var/www/caspay-all
git clone --branch codex/admin-dashboard --single-branch https://github.com/Finuseco/cashpay-admin.git /var/www/caspay-all/admin
cd /var/www/caspay-all/admin
npm ci --ignore-scripts
npm run check
ADMIN_INSTALL
```

Exécuter les commandes successivement et s’arrêter à la première erreur. Le premier contrôle ne doit pas être ignoré. Cette branche est le correctif préparé ; aucun merge sur main n’est requis ou exécuté par ce guide.

## Environnement privé

Le helper JavaScript peut initialiser **un nouveau fichier `.env` admin**, sans écraser un fichier existant ni modifier celui de Cashpay Web :

```bash
node deploy/configure-env.js /var/www/cashpay-all/wallet/.env
```

Le chemin source ci-dessus vient des logs fournis et doit être confirmé sur le VPS. Seules les variables `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SCHEMA`, `DB_SSL` et `DB_SSL_CA` sont reprises. Un secret de session admin indépendant est créé ; ni le JWT client ni les autres clés du fichier source ne sont copiés. Aucun contenu secret n’est affiché. Le fichier cible est créé en mode `0600` et l’exécution refuse de l’écraser. Les caractères sont contrôlés par un aller-retour du parseur d’environnement Node avant écriture.

Un compte SQL de lecture dédié reste préférable. Le helper peut reprendre l’accès existant pour préparer la connexion demandée, mais n’accorde ni ne révoque de droits SQL et n’effectue pas de migration. Le pool de l’application impose les transactions en lecture seule.

## PM2 et Nginx

Après validation de l’environnement et du port :

```bash
pm2 start deploy/ecosystem.config.cjs
curl --fail http://127.0.0.1:8010/healthz
```

`/healthz` prouve uniquement que le processus répond ; tester ensuite la connexion d’un Admin actif et les données de la base. Si un processus `cashpay-admin` existe déjà, inspecter sa configuration avant tout redémarrage ; ce guide ne remplace pas un service existant.

Adapter `deploy/nginx.conf.example` dans un fichier propre au domaine, après contrôle des configurations et certificats existants. Le proxy cible déjà **127.0.0.1:8010**. Valider avec `nginx -t` avant un rechargement Nginx. Ne pas remplacer la configuration du domaine client. Sauvegarder la liste PM2 et configurer son redémarrage au boot uniquement après les essais de l’application.

Ce guide n’atteste pas une installation réalisée sur le serveur. En cas d’accès SSH sécurisé fourni à une session d’exécution compatible, effectuer d’abord l’inventaire réel du VPS avant ces mutations.
